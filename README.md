# PII Guard

Модуль безопасности персональных данных: прокси между системой-потребителем и LLM.
Находит ПД в тексте, маскирует их перед отправкой в LLM, хранит соответствия
зашифрованными и восстанавливает исходные значения в ответе.

Пользовательского интерфейса нет — решение проверяется только через HTTP API.

## Что это

Модуль встраивается между системой-потребителем и LLM:

- находит персональные данные в тексте запроса;
- маскирует их (вид маски настраивается по системе);
- хранит соответствия «маска → исходное значение» зашифрованными;
- восстанавливает исходные значения в ответе LLM, если системе разрешено демаскирование.

## Быстрый старт в Docker Compose

1. Скопируйте `.env.example` в `.env` и заполните ключи:

   ```bash
   cp .env.example .env
   ```

2. Сгенерируйте ключи шифрования и HMAC (команда есть в `.env.example`):

   ```bash
   python -c "import base64,secrets;print(base64.b64encode(secrets.token_bytes(32)).decode())"
   ```

   Полученные значения впишите в `PII_ENCRYPTION_KEY` и `PII_HMAC_KEY`.

3. Запустите:

   ```bash
   docker compose up -d --build
   ```

4. Проверьте живость и готовность:

   ```bash
   curl http://localhost:8000/health
   curl http://localhost:8000/ready
   ```

Порт на хосте задаётся через `PII_PORT` (по умолчанию `8000`). Внутри контейнера
сервис слушает порт `8000`.

### Запуск без Docker

Требуется Python 3.11. Установка с зависимостями для разработки:

```bash
pip install -e ".[dev]"
```

Запуск:

```bash
gunicorn -c gunicorn.conf.py pii_guard.main:app
```

## Контракт POST /process

Эндпоинт для проверяющей системы. Не требует ключа, использует профиль `checker`
(маска `full` — только звёздочки).

Маскирование:

```bash
curl -X POST http://localhost:8000/process \
  -H "Content-Type: application/json" \
  -d '{"payload": "Клиент Иванов Иван Иванович, паспорт 4509 123456", "payload_id": "abc123"}'
```

Ответ: `{"result": "<замаскированный текст>"}`.

Демаскирование — тот же `payload_id`, в `payload` передаётся полученная маска:

```bash
curl -X POST http://localhost:8000/process \
  -H "Content-Type: application/json" \
  -d '{"payload": "<маска из предыдущего ответа>", "payload_id": "abc123"}'
```

Ответ: `{"result": "<исходный текст>"}`.

Логика ответа по одному `payload_id`:

- записи нет — текст маскируется, соответствие сохраняется, возвращается маска;
- повтор того же текста — возвращается та же маска;
- пришла наша маска — возвращается исходный текст;
- пришёл текст с фрагментами нашей маски — восстанавливаются однозначные фрагменты
  (фрагменты маски из одних звёздочек не восстанавливаются);
- пришёл новый текст без фрагментов маски с тем же `payload_id` — он маскируется
  заново, соответствие перезаписывается.

Коды ошибок:

- `4XX` — некорректный запрос (например, `422` при невалидном теле, `400` при битом JSON);
- `413` — тело больше `PII_MAX_BODY_BYTES`;
- `429` с заголовком `Retry-After` — превышен лимит одновременных запросов.

## Как устроено

Пайплайн обработки текста:

```
нормализация → распознаватели → разрешение пересечений → маскирование
             → зашифрованное хранилище → демаскирование
```

- **Нормализация** сохраняет длину: позиции спанов общие для исходного и
  нормализованного текста.
- **Распознаватели**: регулярные выражения, валидаторы контрольных сумм
  (алгоритм Луна, ИНН, СНИЛС), словари (города, типы улиц, известные люди),
  морфология pymorphy3 (теги Name/Surn/Patr/Geox), контекстные слова.
- **Разрешение пересечений**: при пересечении спанов побеждает более высокий
  балл, при равенстве — более длинный.
- **Маскирование** — виды маски:
  - `full` — каждый символ значения заменяется на `*`, длина сохраняется;
  - `partial` — остаются первые и последние значимые символы (настраивается по
    типу), ФИО и держатель карты — инициалы, email — первый символ локальной части;
  - `label` — `[ПАСПОРТ]`;
  - `token` — `[ФИО_1]`: номер растёт по типу, одинаковые значения получают один токен;
  - `synthetic` — правдоподобные подставные значения того же типа и формата.

При `synthetic` LLM видит естественный текст: подставные ФИО и города даются в
именительном падеже. При демаскировании подставные значения заменяются исходными,
в том числе в изменённом ответе LLM, если значение повторено без изменений.
- **Хранилище**: соответствия шифруются AES-256-GCM, исходный текст целиком не
  хранится (собирается из маски и замен), хранится HMAC-отпечаток исходного текста.
  В Redis запись идёт через `SET NX` с TTL; при недоступности Redis используется
  резерв в памяти процесса и флаг деградации в `/ready`.
- **Демаскирование** восстанавливает текст по позициям.

Производительность:

- gunicorn с uvicorn-воркерами, `preload_app`;
- движок выполняется в `asyncio.to_thread`, чтобы не блокировать воркер;
- одновременные запросы ограничены (`PII_MAX_CONCURRENT_PROCESS`), сверх лимита —
  `429` с `Retry-After`;
- суммарный объём текста в обработке ограничен (`PII_MAX_INFLIGHT_CHARS`), сверх
  объёма — тоже `429` с `Retry-After`.

## Гибридное распознавание: правила + NER

Правила отлично ловят документы, карты и телефоны по контрольным суммам, но пропускают
ФИО и адреса вне словарей и без маркеров: «жду доставку на Тверскую 17», «Нгуен Ван Тхань».
Второй этап — NER-модель `LLAIMlegal/ru-legal-ner` (29 млн параметров, работает на CPU).

Схема «модель предлагает — правила решают»:

- модель даёт кандидатов `PER` и `ADDRESS`;
- правила решают, ПД ли это: фильтры публичных лиц, отделений банков и офисов, морфология;
- адрес от модели маскируется по отдельным словам и числам без служебных слов;
- номера документов, карт и телефонов остаются на правилах с контрольными суммами.

Маршрутизация: сначала всегда правила. Модель пропускается, если правила покрыли все слова,
текст длиннее `PII_NER_MAX_CHARS` или свободный слот модели не освободился за `PII_NER_WAIT_MS`
(исходы видны в метрике `pii_ner_total`). Совпадение с кандидатом правил того же типа даёт
`+0.2` к баллу. Демаскирование модель не вызывает.

Настройки: `PII_NER_ENABLED`, `PII_NER_MODEL`, `PII_NER_THREADS`, `PII_NER_MAX_CHARS`,
`PII_NER_CONCURRENCY`, `PII_NER_WAIT_MS` и флаг `ner` у систем в `config/systems.yaml`.

Качество на внешнем наборе `hivetrace/pii-bench` (1090 документов с ПД, 378 без ПД;
запуск `python -m eval.pii_bench --ner`, отчёт `eval/out/pii_bench.md`):

| Конфигурация | Документы с утечкой (95% ДИ) | Лишние маски на текстах без ПД (95% ДИ) | Время на текст |
|---|---|---|---|
| только правила | 3,4% (2,5–4,6) | 0,5% (0,1–1,9) | 0,4 мс |
| правила + NER | 1,7% (1,0–2,6) | 0,8% (0,3–2,3) | 5,1 мс, p95 9,5 мс |

Адреса полностью закрыты в 164 из 176 случаев (149 без модели), ФИО — 228 из 228, CVC — 73 из 77,
паспорта — 119 из 120. Правила адреса (номер дома без «д.», подъезд и этаж, улицы без маркера по
словарю `data/dicts/streets.txt`), CVV и паспорта подбирались по разборам ошибок на половине набора;
на второй, отложенной половине утечка 1,9%. Из оставшихся 18 утечек 9 — адреса офисов, которые
сервис намеренно не маскирует (адрес организации — не ПД).

## Настройка систем-потребителей

Конфигурация в `config/systems.yaml` и `config/pii_types.yaml`.

`config/systems.yaml`:

```yaml
defaults:
  mask_style: partial
  unmask: true
  strict: false

systems:
  crm-assistant:
    enabled: true
    pii_types: all
    mask_style: token
    strict: true
    api_key_sha256: "<sha256 ключа системы>"
  marketing-bot:
    enabled: true
    pii_types: [PERSON, PHONE, EMAIL, CARD_NUMBER, PIN]
    mask_style: label
    unmask: false
    api_key_sha256: "<sha256 ключа системы>"
    rules:
      - type: PIN
        requires_any: [CARD_NUMBER]
```

Поля системы:

- `enabled` — включена ли система;
- `pii_types` — `all` или список типов ПД;
- `mask_style` — `partial`, `label`, `token`, `full` или `synthetic`;
- `unmask` — разрешено ли демаскирование;
- `strict` — строгий режим: пороги срабатывания распознавателей ниже;
- `api_key_sha256` — SHA-256 ключа системы;
- `rules` — правила сочетаний (например, ПИН маскируется только вместе с номером карты);
- `irreversible_types` — типы ПД, которые маскируются, но не сохраняются для
  демаскирования (например, `[CVV, PIN]`): по требованиям PCI DSS CVV и ПИН нельзя
  хранить после авторизации даже в зашифрованном виде.

`config/pii_types.yaml` — настройки частичной маски по типам и пользовательские типы:

```yaml
partial_specs:
  PASSPORT: {keep_start: 2, keep_end: 2}
  CARD_NUMBER: {keep_start: 4, keep_end: 4}

custom_types:
  VEHICLE_PLATE:
    label: ГОСНОМЕР
    description: Госномер автомобиля
    rules:
      - regex: "(?<!\\w)[авекмнорстух]\\d{3}[авекмнорстух]{2}\\s?\\d{2,3}(?!\\d)"
        base_score: 0.2
        context: [госномер, гос. номер, г/н, грз, номер автомобиля, номер машины]
        context_bonus: 0.6
```

Генерация ключа системы:

```bash
python -m pii_guard.config.keys new
```

Команда выводит `key` (передаётся системе-потребителю) и `sha256` (кладётся в
`api_key_sha256`). Конфиг перечитывается автоматически при изменении файлов
(с интервалом) или по `POST /admin/reload`.

**Краткая инструкция по настройке.** Сгенерируй ключ командой `python -m
pii_guard.config.keys new` и передай открытый ключ системе-потребителю — он идёт в
заголовке `X-API-Key`. Добавь систему в `config/systems.yaml` с `enabled: true` и
`api_key_sha256` из вывода; чтобы отключить систему — `enabled: false`. Типы ПД
задаются в `pii_types`, вид маски — в `mask_style`, демаскирование включается и
отключается полем `unmask`. Сервис сам перечитывает конфиг через несколько секунд
после изменения файла или сразу по `POST /admin/reload` с заголовком
`X-Admin-Token`. Проверь доступ запросом к `/api/v1/mask`.

## LLM-прокси POST /v1/chat/completions

OpenAI-совместимый прокси. Требует заголовок `X-API-Key` с ключом системы.

Обработка запроса:

- все сообщения маскируются;
- выполняется повторная строгая проверка замаскированного текста на утечки;
- вызывается LLM;
- ответ восстанавливается (если системе разрешено демаскирование).

Ответ содержит блок `pii_guard` с полями `system`, `llm`, `masked_messages`,
`llm_answer_masked`, `entities`, `recheck_masked`.

Настройка LLM — переменные `PII_LLM_BASE_URL`, `PII_LLM_API_KEY`,
`PII_LLM_MODEL`, `PII_LLM_TIMEOUT_SECONDS`. Если `PII_LLM_BASE_URL` пустой,
работает встроенная заглушка LLM.

Также доступны `/api/v1/mask` и `/api/v1/unmask` (с `X-API-Key`): маскирование
текста с сохранением соответствия по `session_id` и его восстановление.

## Наблюдаемость и безопасность

- `/metrics` — метрики Prometheus: `pii_requests_total`, `pii_request_duration_seconds`,
  `pii_stage_duration_seconds`, `pii_tokens_total`, `pii_entities_total`,
  `pii_store_degraded`.
- JSON-логи без ПД: из событий удаляются ключи `payload`, `text`, `result`,
  `original`, `masked`, `body`, `content`. Пишутся события `request`, `process`,
  `mask`, `unmask`, `chat`, `llm_fallback`, `invalid_request`, `http_error`,
  `unhandled_exception` и другие — без значений полей.
- Каждый ответ содержит заголовок `X-Request-ID`.
- Тесты на отсутствие утечек ПД в логи, метрики и ответы об ошибках —
  `tests/test_pii_leaks.py`.
- Соответствия шифруются AES-256-GCM; ключи систем хранятся только как SHA-256.
- Админ-эндпоинты `/admin/config` и `/admin/reload` отключены, пока не задан
  `PII_ADMIN_TOKEN`.
- Размер тела ограничен `PII_MAX_BODY_BYTES` (сверх лимита — `413`).

## Ограничения и планы

- На CPU модель работает только для текстов до `PII_NER_MAX_CHARS`; длинные проходят правилами.
- Сильные модели (GLiNER2.5, OpenAI Privacy Filter) подключаются тем же интерфейсом при наличии GPU.
- Фрагменты маски из одних звёздочек в изменённом тексте не восстанавливаются
  (из них нельзя однозначно понять исходное значение).
- Резерв в памяти у каждого воркера свой (общий только Redis).
- В чат-прокси нет стриминга и tool calls.
